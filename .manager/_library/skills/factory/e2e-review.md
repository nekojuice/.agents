## 1. 摘要

`e2e-review` 是 agent E2E／互動審查的 worker 規則：依上級給的清單實際操作受測系統（透過畫面或 API），以值證據與截圖逐項判斷，記錄清單外的 UI 問題與寫入追溯，交出附證據的報告。它是人工驗收前最後一道 agent 自檢，不取代人工驗收；報告只建議每項狀態，算不算完成由上級決定。上級在自動化流程中是派工的 orchestrator（例如 factory），直接呼叫時是使用者。

skill 本身不含任何專案資訊；專案知識全部放在專案的 `.e2e/`（從 `.e2e/PROJECT.md` 讀起）。受測系統的每個可操作部分是一個 **surface**，登記在 `.e2e/config/env.json` 並指定 driver；skill 附 `playwright`（網頁畫面）與 `http`（API）兩個 driver。腳本依使用累積成三層（即興、碎片、固化 scenario），另有含 agent 手動步驟的 recipe，recipe 現階段不作驗收依據；測試資料透過系統自身的 API 準備，不直接寫 DB。所有會寫入者先以 `--dry` 試跑，driver 在試跑時另有攔截寫入的防線；試跑不需要測試資料寫入權限。

1.3 補上實務規則：測試資料寫入權限以 `data_write` 表示、可指定回合種類 `round_kind`；worker 只用為 E2E 建立的帳號，既有帳號除 PROJECT.md 登記的受保護帳號外不使用；驗證需要改動的紀錄一律以 API 新建專用資料，全系統唯一的設定只在 `data_write` 指名時可改並須還原；留下的測試資料要能辨識回合與 worker。工具面新增網頁上的預演（`run --rehearse`）、附理由與證據更正單一 check（`amend`；判定程式有錯而重跑會再寫入時，以即興腳本讀既有值檔重算後再 `amend`）、同一回合跑多支 scenario 各自取代自己的條目、寫入步驟失敗後略過後續寫入、依步驟宣告（`expects`）歸屬稽核紀錄、報告語系，以及回傳的 `assets_changed`。

步驟順序：

1. 啟動：讀 `.e2e/PROJECT.md`，跑 `check`；版本不符或版面警告記入 issues 不停工；driver 或環境不可用時回報上級，不安裝、不啟服務；確認必要輸入。
2. `new` 建立回合資料夾 `<parent>/e2e-review/<yyyyMMdd-HHmmss>-r<NN>-<short>/` 並設為目前任務；可用 `check --out` 把啟動檢查存入回合。
3. 有 web surface 時 `open`；執行對應 scenario，或以 `run <surface>:<fragment>` 組合碎片；含 agent 步驟的流程依 recipe 以 `step`／`log` 執行。
4. 以 `peek`、`api`、`scratch/` 腳本或單一瀏覽器指令即興補缺；網頁上要試一個存檔前會取消的互動時用 `run --rehearse`。
5. web surface 上做清單外 UI 檢查；`run web:probes/shot --name=final`。
6. 以 `add` 補記 UI findings、issues、limits、observations、writes、items。
7. 檢視 `scratch/` 決定升級（含 request 範本與 recipe 草稿）。
8. `close <round> --users=<account keys>`（可加 `--actions`、`--system`）抓稽核紀錄並產生 `report.md`；回傳上級。

專案沒有 `.e2e/` 時：由 orchestrator 在標準化專案派工者走初始化交接（照樣即興審查、產出 `init-proposal`、經上級核准後下次 `init-apply`）；使用者直接呼叫者不初始化，只在執行工作區即興進行。兩種情況下工具都提供隱含的 `web`（`--url`）與 `api`（`--api-url`，不帶登入）surface。

在工廠流程中，本 skill 由獨立 E2E worker 執行（Check 之後、人工 E2E 之前），`orchestrator-factory` § 5b 以固定的 prompt 形狀派工（含 `round_kind`、`data_write`、`init_apply`），讀回傳的 `assets_changed` 與 `writes` 對照授權，並以覆寫 8–9 規定報告父資料夾與 `.e2e/` 的歸屬。

## 3. 其他

### 與 `orchestrator-factory` § 5b 的介面核對

核對 `orchestrator-factory` version 1.12 的 § 5b（開頭兩條、第 1–7 步、`.e2e/` assets 段、E2E worker prompt）、Hard rules 5、Repair policy 的 E2E 段與 Factory overrides 8–9，對照 e2e-review 1.3。**主要介面相符**，未發現互相矛盾的規定；1.2 對照時的「回合種類」落差已解，其餘差異多屬單邊未寫，列在下方「落差」。

相符處：

- **必要輸入**：prompt 的 `checklist`（編號與原文）、`report_parent: run_dir`、`round_kind`（`review`／`prep`／`init`）、`data_write`（`none` 或使用者允許的測試資料，註明 `.e2e/` 與回合資料夾一律可寫）、`accounts / environment`（僅在 PROJECT.md 未涵蓋時）、`previous_round`、`round_basis`、`init_apply` 逐一對應 E9 的各列，名稱與預設值一致；報告父資料夾固定為 `run_dir`，worker 建立 `run_dir/e2e-review/`（覆寫 8）與 E9、E63 一致。工廠一律傳項目編號，E9「清單無編號時由上級定規則」的情況在工廠流程不會發生。
- **`data_write` 與寫入核對**：工廠讀回傳的 `writes`，把測試資料寫入與 `data_write` 核對，超出即阻擋；e2e-review 要求全系統設定只在 `data_write` 指名時可改、改動與還原都記為寫入（E74），兩邊可對得上。
- **`assets_changed`**：e2e-review 回傳新增 `assets_changed`（E32），工廠 `.e2e/` assets 段讀它並列在 run 中；對照授權時只核對測試資料，`.e2e/` 一律可寫，兩邊一致。
- **試跑與預期副作用**：工廠 § 5b 開頭寫試跑及其登入、登出、開頁、查詢稽核紀錄屬預期副作用，沒有測試資料寫入權限也可試跑；與 E12、E15 一致。
- **prep 回合**：工廠「驗收需要尚不存在的測試資料時先派 `prep` 回合」對應 E20、E58；prep 無 check 的回傳（`verdict: inconclusive`、無 items、`notes` 帶回合種類）由工廠依種類解讀即可。
- **帳號**：工廠只在 PROJECT.md 未涵蓋時傳 `accounts / environment`；e2e-review 要求需要管理員角色時由派工或 PROJECT.md 指明 E2E 帳號，無 PROJECT.md 時只用上級指定的帳號鍵（E73），由同一欄承載。
- **surface**：§ 5b 不指定 surface，交由 `.e2e/PROJECT.md` 與 `env.json` 決定；「同一環境同時只有一個 E2E worker」與 E16 的「跨所有 surface 單一操作者」一致。
- **回傳區塊**：prompt 指定 `return: E2E_REVIEW_RESULT_V1`，即 E32；1.3 只新增 `assets_changed` 一欄，其餘欄位未變。
- **狀態**：§ 5b 處理 `product-fail`（修正回合 → 重新 Check → 以 `--prev` 與修正為 basis 再派下一回合，對應 E31）、`run-error` 與 `needs-human`（重派或交人工；Repair policy 明言 `run-error` 不當產品失敗）、`verified-with-limits`（只勾已驗部分、limit 留為人工項）；第 2 步禁止 orchestrator 把 worker 未標 `verified` 的項目自行當成已驗證，與 e2e-review「上級決定什麼算完成」相容；`needs-input` 對應工廠的 `needs_input`，`blocked` 兩邊都定為環境或 driver 不可用（工廠第 5 步、E9）。項目狀態五值與回傳狀態三值都有落點。
- **依 agent 步驟判定的 `needs-human`**：e2e-review 讓這類項目即使 check pass 仍為 `needs-human`（E72），回傳行內註明並說明重跑不會改變（E32）；§ 5b 第 4 步對應為此類項目一律不重派，所有未解決項目在人工 E2E 關卡以一份統一報告交給人。標示方式在 e2e-review 只是範例措辭（「agent step: …」），不是固定標記，orchestrator 需從行文判讀；報告的人工工作欄另寫「依 agent 步驟判定，需人工確認」可供核對。
- **寫入範圍**：prompt 的 constraint「只寫 `.e2e/` 與 `run_dir/e2e-review/`、不改產品、不 commit、問題交 orchestrator」與 E8、E11 相同；`.e2e/` 變更歸入 run 的 change set、由 orchestrator 依規則 commit（覆寫 9）對應 E11、E35。
- **初始化**：`init_needed: yes` → orchestrator 在下一個人工關卡呈現 proposal → 使用者核准後派 `init` 回合（`round_kind: init`），以 `init_apply`（proposal 所在回合資料夾與核准者）指示，對應 E19 的 `init-apply <round> --approved-by=<who>`。工廠要求一律經使用者核准，比 E19「必要時由上級問使用者」嚴格，兩者相容。
- **內部委派**：Role 段「E2E worker 可依 `e2e-review` 允許派 sub-worker，只有它操作受測系統」與 E33 一致。

落差（不構成矛盾，但兩邊都沒寫清楚）：

- **回合種類**（已解（1.3））：工廠 prompt 已有 `round_kind`，§ 5b 寫明何時先派 `prep` 回合；e2e-review 必要輸入表已有 `round_kind` 一列並傳給 `new --kind`，prep／init 無 check 與有 check 時的回傳都已寫明（E9、E29）。
