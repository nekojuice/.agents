## 1. 摘要

實作後的「硬閘」檢查：找出並執行專案實際的編譯／建置、單元測試、lint，以及（適用時）獨立的型別檢查，回報 pass／fail／skip 與證據。不判斷需求邊界。預設唯讀，只回報、不自動修復。

單獨使用時只在使用者明確呼叫時執行，不自行主動執行，可在任何時間點跑。當某個流程 skill 或派工指示明列本 skill 為必要步驟時，視同明確呼叫，且該流程的覆寫條款優先；單獨使用的預設不變。在工廠流程中，`orchestrator-factory` 把它設為 apply worker 的出口閘，並以覆寫條款改變觸發、修復、報告位置等預設。

執行順序：決定目標模組（使用者指定 → 對話脈絡 → git 變更 → 詢問）→ 每個模組逐類別探索指令（使用者指定 → 模組 scripts／建置定義 → CI 設定 → 慣例預設 → 卡住就詢問）→ 執行四類檢查 → 依固定六段格式在對話中回報 → 停下等使用者指示。

## 3. 其他

- 本 skill 沒有 anti-cheat 規則。`opsx-apply-guide` 的 anti-cheat 涵蓋所有 apply session（含修復硬檢查失敗）；但在 apply 流程之外單獨使用本 skill、使用者要求修復時（E4、E13），本 skill 沒有條文禁止以弱化或刪除測試讓檢查變綠。
- 報告格式（E12）只呈現本次執行結果，不呈現測試本身是否在這次變更中被修改；本 skill 未宣稱能判斷綠燈是否來自被弱化的斷言。
- E3 讓流程的覆寫條款優先，但本 skill 沒有列出哪些預設可被覆寫；可覆寫範圍完全由呼叫端流程決定。
