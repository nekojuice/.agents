# 協助外行人形成可討論的需求

這是 [cognitive-work-sharing](../SKILL.md) 的參考文件，供工程師、需求參與者與 agent 共同使用。[English](requirements-discovery.md) 提供相同指引。本 skill 仍須明確調用；本文件不授予實作、派工或替需求者決定的權限。

## 1. 需求尚未成立時，協作要完成什麼

外行人可能不知道技術能做到什麼，也不知道自己真正想要什麼。邀請他提出需求，不代表他已經能描述成果、邊界、例外或驗收條件。

這個階段要協助各方形成共同可檢視的問題與預期結果。不要把尚未釐清的想法直接視為工程任務，讓工程師默默承擔猜測偏好、補齊情境、選定目的與劃定範圍的責任。

這是依本框架使用者經驗整理的協作指引，不是已經實證驗證的通用需求方法。以「需求尚未成形」描述狀態，不把外行人當成固定的人格類型。同一個人在陌生領域也可能無法描述自己要什麼。

## 2. 辨認一句話的成熟程度

會議中的陳述可能是不同材料，不能因為語氣肯定就視為已定案。

| 材料 | 意義 | 接下來要釐清什麼 |
| --- | --- | --- |
| 問題 | 某件事正在造成困難 | 發生情境、影響與目前處理方式。 |
| 願望 | 希望工作變得更好 | 哪種改變才算有用，對誰有用。 |
| 靈感 | 值得探索的可能性 | 它對應哪個問題或機會。 |
| 方案猜想 | 對解法的初步想像 | 為何選這種做法，還有哪些成立條件。 |
| 已確認需求 | 各方已確認的預期行為或成果 | 適用範圍、驗證方式與尚未決定之處。 |

例如「希望 AI 自動處理所有客訴」，尚不能推定已選定自動回覆、退款判斷或案件分派。工程師或 agent 可以提出解讀，但要標明是假設，並保留來源與確認狀態。尚未反對、會議氣氛熱烈或原型已做出，都不等於需求獲得確認。

## 3. 從具體事件建立共同材料

不要只要求「請把需求講清楚」。改從對方能辨認的經驗切入，按需要追問：

- 上一次發生時，誰在做什麼？
- 卡在哪一步，造成什麼後果？
- 當時怎麼處理，有什麼限制？
- 哪一段最希望改變？改變後怎樣才有用？

沿用已提供的資料，避免重問。問題不必一次全部提出；先取得能改變理解的具體事件。對全新產品或尚未發生的機會，也可以共同構造一個明確標為假設的使用情境，再找可能使用者或其他證據核對。

工程師負責協助抽象化，不要求外行人先寫規格。如果連具體事件、假設情境或想改善的後果都沒有，應說明目前仍在尋找問題，還不足以承諾實作。

## 4. 區分不同的未知

| 尚未知道什麼 | 適合的探索方向 |
| --- | --- |
| 問題在哪裡 | 觀察實際工作、事件與困難。 |
| 想改善成什麼結果 | 比較不同結果會改變誰的工作及其後果。 |
| 如何達到已知結果 | 由工程師調查可行路徑、成立條件與限制。 |
| 看過才知道喜不喜歡 | 用有明確比較目的的草圖、樣本或原型辨認偏好。 |
| 不同參與者想要不同結果 | 揭露衝突與影響，交由有權責的人取捨。 |

一件事可以同時包含多種未知。不要用技術實驗回答價值取捨，也不要用多做幾個版本掩蓋尚未處理的意見衝突。

## 5. 讓對方理解能力、完成程度與邊界

用「原本如何工作，之後會如何改變」展示能力，包含輸入、產物與人的參與位置，再解釋為何做得到。案例應幫助對方類推，不只是列出技術名詞或吸引人的功能。

說明「做出來」的完成程度：概念展示、可操作原型、約定條件下可使用的成果，以及包含維護與異常處理的持續運作系統，代表不同承諾。不要讓原型外觀暗示尚未具備的可靠性。

把邊界說成可理解的條件與後果：

- **能力**：哪些已驗證，哪些仍須實驗。
- **成立條件**：需要哪些資料、權限、工具與領域知識。
- **可靠性**：什麼能檢查，剩下哪些錯誤可能，錯了影響什麼。
- **交付責任**：本次做到哪裡，誰確認結果，後續由誰維護。

外行人不必自行發明這些邊界；工程師提出具體說明，需求參與者協助確認工作事實、期待與可接受後果。技術可以組合，不代表組合後的品質、成本與時程都已成立。

## 6. 每次探索要回答一個可辨認的問題

製作草圖或原型前，先說明要辨認什麼，以及不同結果會如何改變下一步。探索的交付物可以是排除某方案、確認一個前提或辨認偏好，不必是更多功能。

例如兩張草圖可用來確認「主要按案件處理，還是按客戶處理」。若這會改變資訊組織方式，就值得比較。不需要先實作兩套完整系統再請人挑選。

如果展示只持續引出新功能，沒有排除選項、確認條件或形成判準，agent 應指出探索尚未收斂，整理新增想法與目前問題的關係，不把全部想法直接加入承諾範圍。是否擴大探索，由既有權責與授權決定。

## 7. 會議應留下可續接的進展

不要求每次定案，但結束時應更清楚知道：

1. 正在處理的問題或機會，以及影響誰。
2. 已確認的理解、暫定假設與尚未決定的取捨。
3. 剩餘未知需要觀察、調查、示範，還是權責者決定。
4. 下一步探索預期讓哪個決定成為可能，以及做到哪裡就足夠。

沿用既有專案紀錄，不另建平行的需求正本。若沒有足夠共識，明示沒有定案；不要為了寫出漂亮結論而補造一致意見。討論中的新靈感也不必全部進入下一步。

## 8. Agent 如何分擔，而不代替人決定

Agent 可以在授權範圍內整理陳述、回查既有決策、找出矛盾、擬出假設情境、調查可行性，並建議最能釐清未知的下一步。優先處理可查明的材料，再提出真正需要人表達意圖或作取捨的問題。

保留原始陳述與整理後解讀的差別。不要把推論寫成使用者原話、將探索方向升格為交付要求，或以技術可行取代業務上的選擇。需要確認時，提出具體解讀與其後果，讓對方能修正，而不是要求他從空白開始寫完整規格。

成效應看：各方是否更能指出在解決什麼、哪些已確認、哪些仍未知，以及下一步能回答什麼。功能清單變長、原型變多或會議更熱烈，都不足以證明需求更清楚。
