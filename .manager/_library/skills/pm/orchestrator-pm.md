## 1. 摘要

`orchestrator-pm` 是專案的 PM 控制面：維持長期方向與狀態、協調有界的唯讀調查、整理事實與決策，並在人工核可後準備工廠交接；自己不實作產品、不做工廠的工作。它只管專案層級的方向、範圍、排程與狀態，工廠粒度的研究、設計與實作問題留給工廠。只在使用者明確呼叫或明確啟用 PM 模式時進入，依主題載入 `pm-status-review`、`pm-intake-triage`、`pm-investigation-worker`、`pm-factory-handoff`。PM 發動的工廠委派預設使用 `peer-agent-coordination`（使用者核可委派即視為啟用），其他情況只在使用者提及或與使用者的協作討論需要時才用。使用者核可自動化計畫時，PM 以一個 manager run 管理一整批工廠 run。受管對象不是程式碼時（例如 skill 包、文件集），走「非產品路線」：由 manager session 依 `references/non-product-route.md` 的八個步驟直接修改受管對象，不經工廠。除了初次進入時的初始化，所有正典更新一律先擬稿到 run 的 `staging/`，使用者檢查後才套用。PM 必要時也可更新工廠根目錄的 `.factory/_review-queue.md` 與 `.factory/_issue-backlog.md`，包括撿走長期未處理的條目後從這兩份檔刪除；`.factory/archive/` 只讀不寫。

流程順序：

1. **進入**：宣告 PM 模式與目標 → 唯讀檢視 `.manager/` → 若不存在，判斷工作區是否已有可觀的專案狀態：有則告知並徵得同意後，先初始化 `.manager/`（含 `_runs/` 與單行 `.gitignore`，只以五個正典檔範本直接建立，不經 `staging/`）並建立 crawl 的 manager run，再把 baseline crawl worker 經 `pm-status-review` 派進該 run，首份狀態與里程碑仍先擬稿，之後依證據討論憲章；無則先討論憲章，再於使用者明確要求時初始化 `.manager/` → 恢復具名 run 時只讀 `_run.md` 與其指向的產物 → 未指名 run 時不在多個 run 間猜測。
2. **路由**：依意圖分派到討論、狀態盤點、里程碑維護、進件分流、調查 worker、工廠交接、批次自動化、撿走工廠長期未處理條目、處理工廠留下的交接檔；要求實作時說明 PM／工廠檢查點，受管對象屬非產品路線時改走該路線。
3. **工作**：需要耐久紀錄時建立 run（`_run.md`、`notes.md`、`outcome.md`、`findings/`，選用 `inputs/`、`staging/`；非產品路線另有 `requirements-comparison.md`、`changes/`、`reviews/`；自動化另建 `_automation.md`）；worker 產物寫在 PM 指定的 run 內路徑，由 PM 比對綜合。
4. **非產品路線**（適用時）：需求對照（預設）→ 與使用者逐輪定案 → 每個目標一份異動決策加索引 → 使用者檢查並指示後直接修改（項目進 `in-delivery`）→ 審查（預設），PM 判斷發現後才修 → 使用者以 git diff 或等效前後對照驗收（項目進 `verifying`）→ manager 影響與狀態提案擬稿到 `staging/`，使用者檢查一次後沖入 → 使用者要求時分開 commit，收尾或拆出新 run。
5. **委派**（適用時）：PM 發動的工廠委派預設在工廠 run 建 peer 討論室、PM 任 host；補交事項以討論室訊息或交付到工廠 run 根目錄的 `handoff-factory-<topic>.md` 傳遞，非自動化時先與使用者討論。
6. **自動化**（適用時）：與使用者議定範圍寫成 `_automation.md` → 使用者核可 → 經 `pm-factory-handoff` 建立每個工廠 run → 設計段 → 使用者一次檢視全部 change → 施工段依相依順序施工（含 Check 與 agent E2E review）→ 整批完成後彙整 `_review-queue.md`、使用者對剩下事項做一次人工 E2E、sync/archive；收尾時完成項目歸檔到 `.factory/archive/`，未完成的 queue 項目與未處理的 backlog 條目留在工廠。
7. **回流**：工廠的 `handoff-manager-<topic>.md` 在人指示或 peer 通知時讀取，篩選後擬稿到 `staging/`，使用者檢查後套用；處理紀錄寫在 PM 自己的 run。工廠不會自行把根目錄兩份清單的條目交給 manager；長期未處理者由 PM 發動撿走（使用者要求或盤點時提出），擬稿到 `staging/`，使用者檢查後寫入 `_backlog.md`，再從工廠兩份檔刪除並記在 run。
8. **收斂**：寫 `outcome.md`，只把已確認內容經 `staging/` 擬稿、使用者檢查後升級為正典（status、backlog、library），記錄工廠交接、非產品修改與已處理的交接檔，標記 run 結束；主題要另外繼續時拆出新 run。
9. **停止**：交付當次 PM 結果或遇到人閘即停；核可的自動化計畫以外不啟動工廠 session；有 peer 討論室的委派依 peer section 5 保持可被喚醒，直到使用者結束討論室。

## 3. 其他

skill 本身：

- **`constraints` 的地位（本輪刻意不改）**：本 skill 把 `constraints` 列為每個 worker prompt 都要提供的欄位；`pm-investigation-worker` 把它列為選用輸入。本輪判定這是提供方與接收方的不同角度，不衝突。
- **`extends` 方向（本輪刻意不改）**：本 skill 的 `extends` 列出子 skill，子 skill（例如 `pm-investigation-worker`、`pm-factory-handoff`）的 `extends` 也列 `orchestrator-pm`。本輪判定 create-skill-guide 把 `extends` 定義為記錄真實關聯，雙向符合定義。
- **`changes/_index.md` 內容兩處寫法不同**：non-product-route § 3 列批次、相依、manager 影響彙總、撰寫時出現的問題；workspace-contract § `changes/` 只列批次、相依、待確認，沒有 manager 影響彙總。
- **異動決策範本的擬稿位置**：change-decision 範本的 Manager impact 仍寫「Drafted in the run」，non-product-route § 7 與 run-lifecycle 寫明 `staging/`。範本本輪列為不改，兩者不矛盾，只是範本未同步用詞。
- **commit 的授權位置**：non-product-route § 8 與 SKILL 路線第 8 步讓 PM 在使用者要求時 commit 受管對象與 manager 正式檔；硬規則 3 的寫入例外、硬規則 4（不得修改 repository）與 authority-and-gates § PM writes 都沒有提到 commit。
- **審查基準不含章程**：non-product-route § 5 與 review-triage 範本的基準順序為使用者定案 > library 決策 > 異動決策；authority-and-gates 的權威順序把章程與已接受決策並列第二級，審查基準沒有提章程。
- **拆出紀錄在 outcome 範本無對應列**：run-lifecycle § Split off a topic 要求在來源 run 的 `outcome.md` 記錄拆出，run-outcome 範本 Promotions 與其他段落沒有對應欄位。
- **`notes.md` 無範本**：run-lifecycle § Create 步驟 3 寫由 assets 實例化 `_run.md`、`notes.md`、`outcome.md`，但 `assets/` 沒有 notes 範本（前版即存在，前版對照未列）。
- **`.factory` 根目錄兩份清單的「必要時」（部分已解）**：撿走條目這一種寫入已有規定：先擬稿到 `staging/`，使用者檢查後寫入 `_backlog.md`，才刪除工廠條目（SKILL § Route the request、authority-and-gates § PM writes）。其他更新仍只寫 when needed（硬規則 3、authority-and-gates、workspace-contract § Ownership），沒有說明何時算必要，也沒有規定寫入前是否需使用者檢查。
- **reviewer 剔除只在範本**：automation 範本 Flow 有 reviewers left out（none／Check／E2E），SKILL § Automation 第 6 步與預先授權段寫成每個 run 都派 apply、Check、E2E worker，未提可剔除；workspace-contract § `_automation.md` 的說明也未列 E2E 測試資料寫入授權（`data_write`）與剔除欄。
- **「長期」未定標準（本輪刻意不改）**：撿走路由只說「長期未處理」，沒有時間或輪數標準；異動決策明定由 PM 與使用者判斷，不寫死。
- **撿走紀錄在 outcome 範本無對應列**：撿走路由要求把撿走記在 run；寫入 `_backlog.md` 可記在 run-outcome 範本 Promotions 的 Backlog 列，但從工廠兩份檔刪除了哪些條目沒有對應欄位，與拆出紀錄的情況相同。

`orchestrator-pm-readme.md` 與 skill 的不一致：

- README 非產品路線流程圖最後是「擬稿到 staging/」→「使用者檢查後沖入、pm-status-review 盤點」，讀起來像沖入之後才盤點；non-product-route § 7 與 run-lifecycle 是狀態與里程碑提案也經 `pm-status-review` 擬進同一個 `staging/`，使用者檢查一次後沖入。
- README 未提到跨方交接檔的格式（開頭三行、收件方不修改、處理紀錄寫在自己的 run）。屬省略，不是矛盾。
- README 的寫入範圍仍寫「例外有三種」，未列硬規則 3 的 `.factory/_review-queue.md`、`.factory/_issue-backlog.md`，也未列撿走時刪除條目；請求路由流程圖已補撿走分支，自動化流程圖已同步收尾歸檔到 `.factory/archive/`、未完成留在工廠。
